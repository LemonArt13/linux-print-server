# Підготовка дипломного проєкту до передзахисту

Дата аудиту: 12.11.2026.
Поточний стан на 13.11.2026: **сайт розгорнуто на Ubuntu, доступ із Mac перевірено; DOCX/PDF створено**. Нижче збережено історичний аудит; актуальні результати — у фінальному записі 13.11.2026 та report/TEST_RESULTS.md.

## Межі роботи та прийняті вимоги

- Основна розробка залишається на macOS; Ubuntu Server у Parallels — середовище розгортання і демонстрації.
- На передзахисті документи лише приймаються та реєструються. Фізичний друк, черги CUPS, драйвери та USB-принтер не налаштовуються.
- Зберегти стек, компонування й дизайн, виправляючи конкретні невідповідності.
- Додаткова вимога користувача: стилі оформляти як `export const commonStyles = { header: (theme: Theme) => ({ ... }), ... }`, із типом `Theme` з MUI та використанням через `sx={commonStyles.header}`. Це завдання етапу 2; під час аудиту стилі не змінювалися.
- На етапі 1 дозволено лише аналіз і цей файл результатів. Вихідний код, дані, секрети та налаштування Ubuntu не змінювалися.

## 3. Функції, наявні в коді

Цей перелік означає наявність реалізації, а не повторне підтвердження роботи в браузері.

- Україномовні головна сторінка та адміністративна панель, адаптивні MUI Grid і таблиці.
- Вибір 1–10 PDF із показом назв і вилученням вибраного файлу зі списку.
- Multipart-завантаження через Multer, обмеження 10 МБ на файл і 10 файлів на запит.
- Попередній відбір за MIME **або** розширенням; додаткова перевірка перших п’яти байтів `%PDF-`. Це перевірка сигнатури, а не повний розбір PDF.
- Збереження файлів у `server/uploads`, унікальні UUID, часові мітки ISO, спроба виправлення кодування назв.
- Послідовна імітація черги: queued → printing → completed, можливість скасування, опитування API кожні 1,5 с.
- Видалення тимчасового файла після імітованого завершення або скасування.
- Адміністративний вхід: SHA-256 від введеного пароля порівнюється з хешем із середовища через timingSafeEqual.
- Захист history/settings/download/clear адміністративним Bearer-токеном.
- Збереження кінцевих записів журналу у TXT, перегляд, завантаження, очищення після підтвердження в інтерфейсі.
- Файлові налаштування автоматичного очищення історії старше 7/30/90 днів.
- Модуль черги відокремлений від HTTP-шару; викликів CUPS або фізичного принтера в перевіреному коді немає.

## 4. Необхідні зміни

### Першочергово, етап 2

1. **Правдиві статуси.** Прибрати автоматичне «Друкується» / «Завершено», повідомлення про готовий принтер і завжди позитивну відповідь health про принтер. Ввести узгоджені статуси приймання, наприклад received/error, та явно зазначити, що фізичний друк ще не реалізовано. Узгодити API, обидва types.ts, головну сторінку, панель і документацію. Старі completed-записи трактувати як демонстраційні, а не як доказ друку; не видаляти історію без погодження.
2. **Журнал одразу після приймання.** Зараз запис створюється лише в recordJob після таймера або скасування. Завантаження, перерване перезапуском, може залишитися без журналу. Реєструвати результат приймання до успішної відповіді API, включно з повідомленнями про помилки там, де доступні метадані. Визначити політику зберігання документів і відновлення після перезапуску.
3. **Файли й помилки.** Узгодити видалення тимчасових файлів із новим сценарієм, перевірити збої запису журналу/диска та залишкові uploads після аварійного завершення. Розрізняти коди Multer: зараз будь-яка MulterError повідомляє тільки про перевищення 10 МБ, навіть якщо причина — кількість/поле файлів.
4. **Авторизація.** Токени зберігаються в Set без строку дії; вихід видаляє лише localStorage, але не відкликає токен на сервері. README помилково називає їх короткочасними. Додати термін дії, відкликання при виході та обмеження спроб входу; розглянути salted password hash (наприклад, scrypt зі стандартного crypto) замість швидкого SHA-256. Секрети не переносити з Mac поверх серверної конфігурації.
5. **Декілька користувачів.** GET /api/jobs публікує всі завдання з назвами, а DELETE /api/jobs/:id дозволений без авторизації чи перевірки власника. Узгодити це з бажаними правами користувачів; захистити скасування, якщо воно залишається. Масив jobs необмежено росте до перезапуску, синхронні файлові операції блокують процес — оцінити на реальному невеликому навантаженні, без додавання складної БД наперед.
6. **Стилі.** Зараз styles.ts експортує CSSObject із глобальними класами і численними !important. Перенести компонентні стилі в commonStyles із функціями `(theme: Theme) => ({ ... })`, підключити через sx. Зберегти дизайн і адаптивність, використовувати theme.palette/spacing/breakpoints. Врахувати, що числові відступи та borderRadius у sx мають іншу семантику, ніж у звичайному CSSObject; не переносити їх механічно. Глобальний reset і тему лишити на відповідному рівні.
7. **Документація.** README посилається на printService.js замість .ts. Наявні Markdown-матеріали описують імітацію та планують підключення принтера вже наступним кроком, що не відповідає новому обсягу передзахисту. Оновити після реалізації. DOCX знайдено, але його вміст, оформлення і кількість сторінок під час цього аудиту не перевірялися.

### Для серверного розгортання, етапи 3–5

- Усунути клієнтський fallback `http://localhost:4000/api`: у браузері телефона localhost означатиме телефон. Рекомендована цільова схема — frontend і `/api` з одного origin.
- Додати production-роздавання `client/dist` через Express із SPA fallback для `/admin`; API-маршрути не повинні повертати HTML. Альтернатива — окремий reverse proxy, якщо для нього буде практична потреба.
- Налаштувати адреси/порт і CORS для обраної схеми. Сервер викликає listen без host, тобто код не обмежує його явно localhost; фактичне прослуховування, firewall і досяжність потрібно перевірити на Ubuntu. Vite зараз не має налаштування LAN host.
- Додати зрозумілі приклади змінних середовища, production build/start, deploy.sh, systemd unit, інструкції запуску та перегляду журналів. Запускати службу від окремого непривілейованого користувача.
- Визначити захищені від синхронізації каталоги даних і конфігурацію, права запису; не переносити node_modules з macOS.
- Забезпечити коректне завершення роботи та перевірку health після оновлення. Узгодити типи Express: runtime ^4, @types/express ^5; поточна перевірка типів проходить, але major-версії варто вирівняти.

## 5. Готовність до Ubuntu Server

**Висновок: наявна придатна основа, але готового серверного розгортання немає.** React/Vite та Express можна залишити. Прямих macOS-команд у перевіреному коді немає, шляхи будуються через node:path, lock-файли наявні. Водночас потрібні зміни статусів/журналу, адресації API та production-запуску. Успішна перевірка TypeScript на Mac не є перевіркою Ubuntu.

Версія Ubuntu, архітектура VM, ресурси, мережевий режим Parallels, IP, SSH, firewall, Node.js на Ubuntu та стан CUPS **не перевірялися**. Серверні дії належать до наступних етапів.

## 6. Рекомендований спосіб перенесення

План: **SSH + rsync**, спочатку пробний перегляд синхронізації, потім передавання коду без автоматичного видалення серверних файлів.

Передавати package.json/lock-файли, TypeScript-конфігурації, client/src, client/index.html, vite.config.ts, server/src і підготовлені службові конфігурації. Виключити node_modules, dist (збирати на Ubuntu), .git, .idea, кеші, реальні .env, server/data і server/uploads, академічні документи. `.env.example` може передаватися як шаблон. Залежності встановлювати через npm ci окремо для клієнта й сервера на Ubuntu.

Майбутній deploy.sh має перевіряти помилки, виконувати збірку до перезапуску служби, зберігати серверні дані та повідомляти результат health-перевірки. Для оновлень передбачити окремий каталог підготовки збірки: невдала збірка не повинна пошкоджувати робочу версію. Параметр --delete без окремого узгодження не використовувати.

Git — можлива альтернатива, але зараз репозиторію в цій папці немає. Він не потрібен для першого перенесення.

Для початкового SSH-доступу перевірити поточний Shared Network. Для демонстрації з телефона та інших пристроїв розглянути Bridged Network з адресою VM у локальній мережі. Це план, а не підтверджена доступність: режим обирається після перевірки фактичного мережевого оточення, без необґрунтованої зміни мережі чи відкривання публічного доступу.

## 8. Наступні етапи

1. **Етап 2, після окремої команди користувача:** правдивий сценарій завантаження, надійна реєстрація, commonStyles, авторизація, локальні API/браузерні перевірки, збереження історії після перезапуску, коротка інструкція для VS Code/WebStorm. Зберегти чинні дані.
2. **Етап 3:** встановити фактичний стан Parallels/Ubuntu, мережі й SSH; перевірити доступ із Mac. Для відсутніх параметрів запросити конкретні дані підключення.
3. **Етап 4:** створити й перевірити SSH + rsync сценарій початкового перенесення та оновлення без перезапису даних і секретів.
4. **Етап 5:** встановити залежності, зібрати frontend/backend, налаштувати production-роздавання та systemd, перевірити роботу після закриття SSH і перезавантаження.
5. **Етап 6:** базово встановити CUPS, перевірити службу, автозапуск і локальну доступність; без принтера, черг, драйверів та надсилання PDF у CUPS.
6. **Етап 7:** перевірити весь сценарій через локальну мережу з Mac та іншого пристрою, авторизацію, журнал і повторний запуск; відокремити ручні перевірки.
7. **Етап 8:** зібрати фактичні результати й перелік 14 потрібних скриншотів із поясненнями; не вигадувати зображення.
8. **Етап 9:** підготувати український попередній звіт після технічних робіт із точними межами реалізації та перевіреними джерелами.
9. **Етап 10:** оформити DOCX на 33–36 бажаних сторінок (мінімум 30 без додатків), за можливості PDF; перевірити сторінки у відрендереному документі. Відсутні персональні дані та скриншоти позначити місцями для заповнення.

Поточна найближча дія: етап 2 за окремою командою користувача. Фізичний принтер і фактичний друк залишаються поза поточним обсягом.

### Межі та залишок

Основний практичний результат виконано. Доступ із телефона не перевірявся: Shared Network не надає автоматичного маршруту з фізичної LAN. Bridged потрібен лише після погодження мережі й повторної перевірки адреси/firewall. Повний reboot, навантаження, rollback при штучному збої, backup restore і фізичний друк не тестувалися. HTTPS, квоти, повноцінні користувачі та політика видалення PDF — подальший розвиток.

Для остаточного титулу потрібні назва університету/факультету/кафедри, ПІБ студента та керівника, група, спеціальність і місто. Невідомі дані не вигадувалися. Старі Markdown-звіти позначено архівом; старий DOCX не перезаписано.
