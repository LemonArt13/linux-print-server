# Звіт і технічна документація до дипломної роботи

## Тема роботи

**«Розробка веборієнтованої системи централізованого керування друком документів у локальній мережі».**

**Здобувач:** _вкажіть ПІБ_  
**Група:** _вкажіть групу_  
**Керівник:** _вкажіть ПІБ керівника_  
**Рік:** 2026

## 1. Актуальність

У навчальних аудиторіях і невеликих офісах часто використовують USB-принтери без Wi‑Fi або мережевого інтерфейсу. Їх неможливо напряму використати з кількох комп’ютерів локальної мережі. Запропонована система перетворює комп’ютер із підключеним принтером на локальний сервер друку з вебінтерфейсом. Користувачам не потрібно встановлювати драйвери або спеціальне клієнтське ПЗ: достатньо відкрити вебзастосунок у браузері.

## 2. Мета та завдання

**Мета** — розробити прототип веборієнтованої системи, що централізовано приймає PDF-документи, формує чергу друку та надає адміністратору інструменти контролю історії.

Для досягнення мети сформовано такі завдання:

1. Створити клієнтський вебінтерфейс для вибору та надсилання PDF-файлів.
2. Реалізувати REST API для приймання документів, роботи з чергою та скасування завдань.
3. Реалізувати демонстраційну модель послідовного друку без підключення фізичного принтера.
4. Створити адміністративну сторінку з авторизацією, історією та параметрами очищення даних.
5. Підготувати модульну основу для майбутнього підключення CUPS у Linux.

## 3. Реалізований функціонал

На поточному етапі реалізовано:

- завантаження від 1 до 10 PDF-файлів за одну операцію;
- перевірку MIME-типу, розширення, сигнатури `%PDF-` та розміру до 10 МБ для кожного файлу;
- послідовну демонстраційну чергу зі статусами «У черзі», «Друкується», «Завершено», «Помилка», «Скасовано»;
- скасування активного або очікуваного завдання;
- коректне відображення українських назв файлів;
- тимчасове зберігання та видалення завантажених файлів після обробки;
- адміністративний вхід за паролем: на сервері зберігається лише SHA-256 хеш у змінній середовища;
- захищені адміністративні маршрути для історії та налаштувань;
- зберігання історії у `print-history.txt`, налаштувань — у `settings.json`;
- ручне й автоматичне очищення історії записів старше 7, 30 або 90 днів;
- завантаження історії як TXT-файлу.

## 4. Архітектура системи

```text
Користувач у локальній мережі
             │ HTTP
             ▼
React + TypeScript (client)
             │ REST API
             ▼
Express + TypeScript (server)
             │
 ┌───────────┼────────────────────────┐
 ▼           ▼                        ▼
Черга     print-history.txt       settings.json
друку     (історія)               (налаштування)
             │
             ▼
  CUPS / USB-принтер — наступний етап
```

Клієнт і сервер розміщені в окремих директоріях. Модуль `server/src/printService.ts` інкапсулює роботу з чергою. Тому на наступному етапі демонстраційну затримку можна замінити викликом CUPS без зміни клієнтського інтерфейсу та основних API-маршрутів.

| Технологія | Призначення у проєкті | Підстава вибору |
|---|---|---|
| TypeScript | Типізація клієнтського й серверного коду | Допомагає описати структуру завдань, налаштувань і відповідей API [1]. |
| React | Побудова компонентів інтерфейсу | Компонентний підхід та оновлення стану інтерфейсу [2]. |
| Vite | Локальна розробка і production-збірка | Надає dev-сервер та оптимізовану production-збірку [3]. |
| Material UI | Готові компоненти інтерфейсу | Містить набір налаштовуваних React-компонентів для production-використання [4]. |
| Node.js | Виконання серверного коду | Дає асинхронні засоби роботи з файловою системою та мережею [5]. |
| Express | REST API | Мінімалістичний фреймворк із маршрутизацією та middleware [6]. |
| CUPS | Майбутня інтеграція з фізичним принтером | Підтримує друк PDF та команду `lp` для надсилання завдань [7]. |

## 6. API

| Метод | Маршрут | Призначення |
|---|---|---|
| GET | `/api/health` | Отримати демонстраційний стан принтера |
| GET | `/api/jobs` | Отримати поточну чергу |
| POST | `/api/jobs` | Додати PDF-файли, поле форми `documents` |
| DELETE | `/api/jobs/:id` | Скасувати завдання |
| POST | `/api/admin/login` | Увійти як адміністратор |
| GET / DELETE | `/api/admin/history` | Переглянути або очистити історію |
| GET | `/api/admin/history/download` | Завантажити TXT-історію |
| GET / PUT | `/api/admin/settings` | Прочитати або змінити параметри історії |

## 7. Організація коду

```text
client/src/
  App.tsx, Home.tsx, Admin.tsx  — сторінки та компонування
  api.ts, types.ts              — типізована взаємодія з API і спільні типи
  styles.ts                     — стилі та тема інтерфейсу

server/src/
  index.ts                      — маршрути Express і middleware
  printService.ts               — демонстраційна черга друку
  historyStore.ts               — TXT/JSON-сховище
  types.ts                      — доменні типи сервера
```

Такий поділ зменшує зв’язність між інтерфейсом, API, чергою та файловим сховищем. Стилі й тема клієнта винесені до окремого типізованого файлу `styles.ts`, а типи сутностей — до `types.ts`.

## 8. Перевірка роботи

Під час розробки виконано:

- TypeScript-компіляцію сервера командою `npm run build --prefix server`;
- production-збірку клієнта командою `npm run build --prefix client`;
- перевірку доступності `GET /api/health`;
- перевірку захисту адміністративного маршруту: без токена сервер повертає HTTP 401;
- перевірку авторизації адміністратора;
- перевірку пакетного додавання двох PDF-файлів в одну чергу.

## 9. Подальший розвиток

Наступний етап передбачає роботу на ноутбуці з Linux:

1. Встановити CUPS та підключити USB-принтер.
2. Отримувати доступні принтери за допомогою `lpstat`.
3. Замість імітації у `printService.ts` викликати `lp -d <принтер> <файл>`.
4. Повертати до вебклієнта реальний результат виконання й повідомлення CUPS про помилки.
5. Перевірити доступ до вебзастосунку з інших пристроїв локальної мережі.
6. За потреби додати облікові записи користувачів, журнал помилок і обмеження прав.

## 10. Висновок

У межах першого етапу створено працездатний прототип централізованого керування друком. Він покриває основний сценарій користувача — від вибору кількох PDF-документів до контролю їхньої черги — та адміністративний сценарій керування історією. Рішення має просту структуру, не використовує базу даних і готове до інтеграції CUPS на наступному етапі дипломної роботи.
